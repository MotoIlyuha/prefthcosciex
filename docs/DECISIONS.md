# Решения, принятые без дизайн‑дока

Формат записи: **Решение** — контекст, выбор, последствия. Каждое решение принято
там, где дизайн‑док (`docs/DESIGN-DOC.md`) или промт задания не дают однозначного
ответа. Номера разделов — по дизайн‑доку.

## D‑001. Проект живёт в корне репозитория, а не в подкаталоге `bayt/`

Промт описывает структуру как `bayt/{client,api,egegen,…}`. Репозиторий называется
`prefthcosciex` и сам является корнем проекта, поэтому вложенный каталог `bayt/`
добавил бы уровень без пользы. Каталоги верхнего уровня — ровно те, что в промте.

## D‑002. Порядок аргументов `generate(seed, difficulty, subtype)`

Дизайн‑док (7.2) объявляет `generate(self, subtype, difficulty, seed)`, промт —
`generate(seed, difficulty, subtype)`. Промт по приоритету выше, поэтому взят его
порядок; `subtype=None` означает «выбери подтип из seed», что нужно планировщику.
Имена полей `Instance` — из дизайн‑дока (`task_no`, `assets`, `answer_kind`,
`checker`, `solution_steps`, `reference_code`, `exam_like`, `meta`).

## D‑003. Уникальность ответа доказывается одним из двух способов

Дизайн‑док (7.1.2) требует единственности, но для «вычислительных» заданий
(например, 7 — объём файла) перебирать нечего: ответ — функция входа. Введено поле
`Uniqueness`:

* `ENUMERATED` — генератор умеет перечислить всё пространство ответов
  (`enumerate_answers`), property‑тест требует ровно одного попадания;
* `FUNCTIONAL` — ответ вычисляется двумя независимыми решателями, и единственность
  следует из их совпадения на всех seed.

Ни один генератор не может «промолчать»: значение обязательно и проверяется тестом.

## D‑004. Два решателя — это `solve_fast` и `solve_naive`

Дизайн‑док допускает `solve_naive → None`, когда наивный перебор слишком дорог.
Чтобы это не стало лазейкой, `None` разрешён только когда параметры экземпляра
выводят перебор за предел; в этом случае property‑тест обязан получить проверку
через `enumerate_answers`. Тест падает, если генератор не даёт ни того, ни другого.

## D‑005. Ключ карточки метода — `tNN:<subtype>`

Дизайн‑док описывает `theory_cards(task_no, subtype_id, …)`. В `egegen` карточки
живут в `egegen/config/cards/tNN.md` секциями `### <subtype>`; секция `common`
используется как запасная. Так методист правит Markdown без разработчика
(требование 16.6), а ключ остаётся стабильным.

## D‑006. Шаблоны формулировок — YAML с обязательным минимумом в 5 штук

`egegen/config/templates/tNN.yaml` валидируется при загрузке: не менее пяти
шаблонов, каждый ссылается на существующий подтип, неизвестный плейсхолдер —
ошибка, а не пустая строка в условии ученика.

## D‑007. Часовой пояс пользователя хранится как IANA‑строка

Дизайн‑док говорит «часовой пояс из настроек», не уточняя формат. Взята IANA‑зона
(`Europe/Moscow`), а не смещение: смещение ломается на переходах и не переживает
смену региона. День пользователя считается от 05:00 в его зоне (4.2).

## D‑008. Идемпотентность начислений — по `idempotency_key` в `transactions`

Дизайн‑док (5.6, 12.5) требует идемпотентности, не задавая ключ. Ключ строится как
`<reason>:<ref_type>:<ref_id>[:<nonce>]`, уникальный индекс в БД; повтор возвращает
исходную транзакцию, а не создаёт новую и не бросает ошибку.

## D‑009. Python 3.12 в контейнерах, 3.11 в песочнице разработки

В контейнере, где собирался проект, установлен Python 3.11; 3.12 поставлен через
`uv python install 3.12` и используется для всех запусков `egegen` и `api`. Образы
Docker — `python:3.12-slim`. Требование стека соблюдено.

## D‑010. CSP запрещает внешние источники целиком

Промт запрещает обращения к CDN из продакшен‑сборки. Вместо «не используем CDN»
это зафиксировано машинно: `Content-Security-Policy` в `infra/Caddyfile` разрешает
только `'self'` (плюс `wasm-unsafe-eval` для Pyodide). Любая попытка подтянуть
скрипт со стороннего домена ломается в браузере, а не проходит незамеченной.

## D‑011. Задание 16: цепочечные рекурренты считаются снизу вверх, а не рекурсией

Шаблон из Приложения B дизайн‑дока (`@lru_cache` + `sys.setrecursionlimit(100_000)`
+ `F(2027)`) на CPython 3.12 падает с `RecursionError`: каждый вызов через
`lru_cache` расходует **C‑уровневый** лимит рекурсии, который `setrecursionlimit`
не поднимает. Измеренный потолок — около 3330 уровней (обычный словарь‑кэш вместо
`lru_cache` доходит до 200 000). В Pyodide, то есть в самом приложении, ограничение
такое же.

Поэтому для рекуррент вида `F(n) = F(n−1) + …` эталонный код и карточка метода дают
**итеративный расчёт снизу вверх** — ровно то, что советует дизайн‑док (6.1 «если n
большое и зависимость от n−1 — считать снизу вверх в массиве»). Рекурсия с
`lru_cache` остаётся там, где глубина мала: `F(n // 2)`, `F(n−1) + F(n−2)`,
функции двух аргументов. Наивный решатель использует словарь‑кэш, поэтому
перекрёстная проверка работает на любой глубине.

## D‑012. Задание 12: длина строки ограничена 600 символами

Дизайн‑док (Приложение A, задание 12) допускает для сложности 5 строки длиной 10⁴
«с закономерностью». Ответ обязан подтверждаться двумя независимыми симуляциями
в пределах 200 мс на генерацию (7.2д), а моделирование строки 10⁴ символов — это
порядка 10⁸ операций. Поэтому длина ограничена 600 символами, что укладывается в
бюджет и остаётся в диапазоне реальных КИМ. Приём «найти закономерность на малых N
и продолжить её» остаётся в карточке метода: он нужен ученику на экзамене, где
строка может быть длиннее.

## D‑013. Задание 9: условие «сумма двух наименьших больше суммы двух наибольших» заменено

В Приложении B пример `a[0] + a[1] > a[-1] + a[-2]` после сортировки строки не
выполняется никогда (`a[0] ≤ a[-2]`, `a[1] ≤ a[-1]`). Генератор использует
выполнимое сравнение с одним наибольшим элементом, а карточка метода предупреждает
о «вечно ложных» условиях.

## D‑014. Ключ YAML `no` переименован в `number`

В YAML 1.1 голый ключ `no` читается как `False`. Этажи в `floors.yaml` нумеруются
полем `number`.

## D‑015. Пороги рангов XP

Дизайн‑док (4.5) называет ранги, но не пороги. Взяты 0 / 500 / 2 000 / 6 000 /
15 000 XP: «Килобайт» — примерно за две недели типичной игры, «Терабайт» — к маю
у самых прилежных. Пороги — в `economy.yaml`.

## D‑016. Начисление XP

XP за верное решение равен базовой награде задания (без множителей), за неверную
попытку — 2 XP. XP копится после кэпа и в экзамене (4.5), не тратится.

## D‑017. Шкала первичных → тестовых баллов между строками таблицы

Промежуточные значения таблицы 2.3 интерполируются линейно; ниже порога 6 баллов
тестовый балл растёт пропорционально от нуля.

## D‑018. Сложность снижается и после «не понял условие»

Дизайн‑док (6.4) снижает сложность только после «не знал, как подступиться»;
промт (чек‑лист раздела 8) требует снижения после «не понял условие». По приоритету
источников снижаются оба; «не понял условие» дополнительно включает чек‑лист условия.

## D‑019. Допуск симуляции экономики

Доход за неделю сравнивается с доком относительно (±15 %). Итог недели сравнивается
как доля недельного дохода: относительный допуск на число около нуля (+25) не имеет
смысла — расхождение в 4 монеты читалось бы как промах на 16 %.

## D‑020. Фокус‑тема куратора гарантированно попадает в план

По формуле 3.2 вес 1,5 не поднимает дорогую тему (15‑е, 4 часа) выше дешёвой
(1‑е, 1 час), и фокус не появлялся бы неделями. Если фокус‑задания нет в плане,
оно занимает слот «Укрепление», когда укладывается в 20 минут.

## D‑021. Эталонный ответ хранится в строке экземпляра

Дизайн‑док (13) упоминает `answer_hash`. Проверка ответа требует нормализации
по типу (пары, два числа, буквы), и хэш нормализованного ввода усложняет чекеры
без выигрыша: эталон и так никогда не покидает сервер. В `instances` хранятся и
`answer`, и `answer_hash`; клиенту не отдаётся ни то, ни другое.

## D‑022. Тренировочный экзамен бесплатный и ни на что не влияет

Раздел 8: «тренировочный режим с паузой и без монет». Читаем «без монет» как «не
стоит монет». Чтобы это не обесценило платные экзамены, тренировочный вариант не
обновляет модель навыков, не участвует в прогнозе и «экзамене‑арбитре», не
уведомляет куратора и не открывает разборы бесплатно.

## D‑023. Уведомления куратору — отдельный лимит

«Не более 2 уведомлений в день» (10) — правило для ученика. Уведомления куратору
о его учениках (9.4) идут отдельным каналом с лимитом 6 в день; правило «30 дней
неактивности» к ним не применяется — родитель может не открывать приложение.
Тихие часы действуют для всех.

## D‑024. Как устроена перепроверка кода на скрытом варианте (7.5.2)

`hidden_seed` порождает вариант того же подтипа, но с другими параметрами условия:
программа честного ученика (с константами из его условия) дала бы на нём «неверно».
Поэтому ожидаемый ответ на скрытых данных вычисляет эталонное решение **этого**
экземпляра — оно несёт параметры видимого условия. Перебираем до 6 скрытых
вариантов, пока эталон не отработает и не даст ответ, отличный от видимого
(для графов 23 имена вершин могут не совпасть). Если подходящего нет или у задания
нет файлов (16, 25), программа запускается на видимых данных и не должна содержать
ответ литералом. Файл B задания 27 собирает воркер (`verify_status=pending`),
после подтверждения доплачивается вторая половина награды в пределах кэпа того дня.
Тест `test_every_code_task_reference_passes_its_own_recheck` проверяет, что эталон
всегда проходит, а `print(ответ)` — никогда.

## D‑025. Сложность заданий в экзамене

Экзамен — «на экзаменационной сложности»: Б и П уровни — 3, В — 4.

## D‑026. Этажи за монеты открываются по порядку, экстерн — любой

Экстерн — «на любой закрытый этаж» (5.5). Покупка за монеты требует открытого
предыдущего этажа: вертикальная карта (11.5) и цена, растущая с номером, иначе
позволили бы «перепрыгнуть» к дорогим темам без базы. Экстерн раз в сутки,
босс — раз в сутки на этаж.

## D‑027. Подсказка диапазона после 5 задач

«Не знаю → подскажем после 5 задач» (11.2). Прогноз по 27 заданиям после пяти задач
почти пуст, поэтому подсказка строится по среднему рейтингу решённых подтипов:
≥ 1150 — C, ≥ 980 — B, иначе A. До подсказки план строится как для B.

## D‑028. Покупки в магазине и `Idempotency-Key`

Ключ транзакции покупки включает `Idempotency-Key` запроса; без ключа каждая
покупка новая. Повтор запроса с тем же ключом возвращает первый ответ (Redis, 24 ч)
и не списывает монеты второй раз (уникальный ключ транзакции).

## D‑029. Недельный отчёт куратору — HTML

«Скачать недельный отчёт (PDF/HTML)» (9.3): отдаём самодостаточную HTML‑страницу
для печати; PDF получается штатной печатью браузера. Серверный PDF‑рендер добавил
бы тяжёлую зависимость без выигрыша для пользователя.

## D‑030. Уровень доступа подтверждает ученик

Куратор принимает приглашение → связь `pending` → ученик выбирает уровень доступа
(по умолчанию «Прогресс» для родителя, «Полный» для репетитора) → `active`. Менять
уровень может только ученик, в любую сторону.
